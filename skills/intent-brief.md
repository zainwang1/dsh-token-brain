# 先对齐，再动手

「不是我要的那种」几乎都不是文笔或技术问题，是动手前没把标准说清。brief 不是文档，是三十秒写清楚的一段结构。

## 一、brief 八项

| 项 | 问法 | 例 |
|---|---|---|
| 交付物 | 要什么形态 | 一段文案、一个 HTML、一次改动、一份表 |
| 受众 | 谁看 | 给老板看，给客户看，只给自己看 |
| 用途 | 用在哪 | 发小红书、进 PR、当面讲 |
| 规模 | 多长多大 | 300 字、一屏、三个文件 |
| 风格 | 什么调子 | 平实、口语、正式、带点狠劲 |
| 必须有 | 不能漏的 | 价格、链接、三个卖点 |
| 明确不要 | 直接排除 | 不要感叹号、不要夸饰、不要表格 |
| 验收 | 怎么算对 | 能直接发、能跑通、能被非技术看懂 |

八项不必每次写全，但交付物、受众、必须有这三项每次都要有。

## 二、缺信息怎么补

按顺序处理，不要停在原地：

1. **能推断就推断**：从上下文、历史偏好、已有文件里推，推到可靠为止。
2. **推断不了才问**：一次最多问三个，只问会改变结果的问题。低价值问题（要不要加表情）直接按默认做。
3. **问不了就给默认**：写明「按 X 处理」，用户不反对就继续。

不要「先做一版再说」又什么都不问——那是拿用户的等待换自己的省事。

## 三、从历史里提取偏好

用户纠正过的点，就是偏好，记下来，默认遵守：

- 不喜欢开头寒暄 → 直接给结果。
- 不喜欢三段式总结 → 结尾不写「总而言之」。
- 要求中文里不夹英文 → 术语除外。
- 指定过字数 → 下次同样题材沿用。

偏好清单只增不重写；发现冲突时以最近一次的明确要求为准。

## 四、用户说「你看着办」

这句话不是省掉对齐，是授权你定。做法：

- 选一个合理默认，直接做到底。
- 交付时用一句话说明关键选择（「按平价路线写的，要高端版我再换」）。
- 不反复确认，不问「这样可以吗」。

## 五、交付前对照

把 brief 八项过一遍，逐项标记命中或偏离：

- 偏离的，改掉，或者交付时说明为什么偏离。
- 「必须有」有一条没写进去，就是没交付。
- 「明确不要」出现一次，等于整份稿作废。

## 六、反模式

| 反模式 | 症状 |
|---|---|
| 先做再问 | 做完才发现方向错，返工更贵 |
| 问一堆小问题 | 用户回答成本比任务本身还高 |
| 默认假设藏着不说 | 用户以为你懂，结果不是 |
| 把「够好」当「对」 | 交付能用但不是想要的那版 |
| 每次重新理解偏好 | 同一个坑踩三遍 |

## 七、一句话原则

先花三十秒说清「要什么算对」，比后面改三版便宜得多。
