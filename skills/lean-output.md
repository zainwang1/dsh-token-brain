# 交付克制

短不是目的，能直接用才是。最短的合格交付，是用户看完就能干活的那一版。

## 一、结构

```
1. 结论或交付物（最前面，占大头）
2. 关键依据（需要时才写）
3. 下一步（需要用户动作时才写）
```

顺序颠倒的常见写法：先复述需求、再讲思路、再解释为什么这样改、最后才给结果。用户要的是最后一节。

## 二、删什么

- 复述用户刚说过的话。
- 「好的」「没问题」「我来帮你」这类过场。
- 对刚看过的代码或文档再描述一遍。
- 不承载信息的清单（「希望对你有帮助」）。
- 把同一件事换三种说法。
- 未经要求的免责声明。

## 三、留什么

- 约束、禁止项、假设。
- 精确标识：文件名、行号、函数、版本。
- 数字与单位。
- 验证结果：跑没跑、过没过、卡在哪。
- 风险提示：会让用户踩坑的那一句。

判断方法：删掉这一段，用户会不会做错事或返工？会，就留。

## 四、代码与命令

- 只给改动的片段，带位置（文件:行号）。
- 整文件重贴只在用户要求或文件很短时做。
- 命令保留原样，包括引号和路径。
- 不为了短把命令截断到跑不了。

## 五、长文交付

- 先给目录或结构（一次），确认后再展开。
- 分节交付，每节自成一段，不依赖前一节的模糊指代。
- 表格优先于散文，步骤优先于说明。
- 字数要求写进 brief，不凭感觉。

## 六、按场景选长度

| 场景 | 长度 |
|---|---|
| 改一个 bug | 一句原因、一句改法、改在哪 |
| 交付一篇稿 | 成稿本身，不改写说明 |
| 方案对比 | 表格，两到三个方案，每个一行取舍 |
| 排查失败 | 结论、证据、下一步 |
| 教学式解释 | 允许展开，但先给一句话答案 |

## 七、反模式

| 反模式 | 后果 |
|---|---|
| 为短而短，答一半 | 用户追问，总量更贵 |
| 用缩写代替术语 | 歧义，来回确认 |
| 只给结论不给依据 | 用户不敢信，要求重做 |
| 每段都加总结 | 输出翻倍，信息不变 |
| 把所有选项都列出来 | 决策成本转移给用户 |

## 八、自检

1. 第一段是不是交付物。
2. 有没有哪一段删掉之后，用户会少知道一件必要的事。
3. 有没有哪一段是在重复我已经说过或用户已经知道的。
4. 长文有没有先给结构。
